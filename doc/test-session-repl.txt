test-session-repl.txt
======================
A single scenario -- stage a 4-note phrase, commit it, play it, then
play a transformed version of it -- typed into all three of this
project's REPL-driven entry points in turn: the plain Clojure REPL,
musics.clj's own nested mu! REPL, and the hosted Forth interpreter
(input.forth). Every line below was actually run, not just written by
hand -- see CLAUDE.md's own "Repo state" section for what each entry
point is and how they relate; this file is a companion to that, not a
replacement for it.

Each section is a genuinely separate process (a fresh `lein repl` /
`lein run -m input.forth`), so there's no live state carried between
sections -- core.repo starts empty each time. All three produce the
same musical result from the same underlying pipeline (musics.clj/
parse -> core.repo -> core.async-engine), which is the actual point of
walking through it three times: same source text, same result, no
matter which door you came in through.


1. Plain Clojure REPL
======================
$ lein repl

(require '[musics :refer :all])

;; (reset) wipes core.repo entirely and re-bootstraps a fresh :ROOT --
;; only needed here because this doc assumes a genuinely empty session;
;; skip it if you're continuing other work.
(reset)

(def r (parse "{verse: !mf c4 d4 e4 f4}"))
;; => #'user/r
r
;; => {:sid :sid1, :ids [:verse]}

(commit! (:sid r))
;; => 2  (tx 1 is :ROOT's own bootstrap commit from (reset); this is
;;        the first real content)

(play-latest!)   ; commit! never moves what (play ...) will read --
                 ; see CLAUDE.md's "Session, the versioned repo, and
                 ; playback" section for why that's deliberate
(connect)        ; opens the MIDI receiver -- "[musics] Connected."

(children :verse)
;; => a 5-element vector: the !mf instruction marker, then the four
;;    Leaf records for c4/d4/e4/f4 (pitches 60/62/64/65)

(play :verse)                          ; the plain phrase

;; times/transpose/shuffle/etc. are pure -- they take and return
;; MATERIAL, never a bare id. sq is the one function that resolves an
;; id against core.repo into that material in the first place.
(play (transpose 7 (sq :verse)))       ; same phrase, up a fifth (+7 semitones)
(play (times 2 (sq :verse)))           ; same phrase, twice through
(play (shuffle (sq :verse)))           ; same four notes, random order

(exit)           ; or Ctrl-D


2. mu! (musics.clj's own nested REPL)
=======================================
$ lein repl

;; dev/user.clj already :refer :all's musics -- (mu!) is unqualified
;; from the very first prompt, no (require ...) needed here.

(reset)

(mu!)
mu=> "{verse: !mf c4 d4 e4 f4}"
;; => {:sid :sid1, :ids [:verse]}
;; A bare quoted musics string stages itself -- no (parse "...") or
;; (s! "...") wrapper needed inside mu!, that's the entire point of it.

mu=> (c1!)
;; => 2   -- commits whatever mu! just staged, via *1 (clojure.main/
;;           repl's own "last result" binding), same as (commit! (:sid *1))

mu=> (play-latest!)
mu=> (connect)

mu=> (inspect :verse)
;; prints the same 5-child structure as (children :verse) did above,
;; formatted for reading rather than returned as a value

mu=> (play :verse)
mu=> (play (shuffle (sq :verse)))

mu=> (exit)
;; leaves ONLY the mu! nested loop, back to the outer user=> prompt --
;; the outer REPL and anything already committed both survive this.
user=> (ids)
;; => (:verse)  -- core.repo is one store; the outer REPL sees exactly
;;                 what mu! committed, nothing scoped to mu! itself.

user=> (exit)    ; or Ctrl-D, leaves the whole process this time


3. Forth (input.forth)
=========================
$ lein run -m input.forth

RESET

;; Bare musics text tokenizes and stages itself here too -- same
;; m/parse call mu!'s bare strings and a plain (parse "...") both go
;; through, no S" wrapper needed for musics text specifically (S" is
;; still how you build an ordinary Forth STRING, e.g. for PLAY!'s own
;; argument below -- musics brackets and S"-strings are two different
;; things that happen to share this Forth's tokenizer).
{verse: !mf c4 d4 e4 f4} >SID COMMIT!
;; leaves the new tx (2) on the stack

DROP             ; stack hygiene -- not required, just tidy
PLAY-LATEST!
CONNECT

;; Ids passed to a musics.clj-bridge word are ordinary Forth STRINGS
;; (S" ..."), auto-coerced to keywords inside each word -- this Forth's
;; tokenizer has no bare :keyword literal syntax at all.
;;
;; Every one of these words pops its args in a fixed order (top of
;; stack popped first) -- id, THEN tx, for anything that takes both,
;; so push id first and tx last:
S" verse" LATEST-TX INSPECT
;; prints the same 5-child structure the other two sections saw

S" verse" PLAY

;; PLAY! stages + commits + plays in one step, straight from a string
;; -- mirrors musics.clj/play-file!'s own recipe. One real gotcha, not
;; hypothetical (see forth.clj's own comment above this word): it only
;; pops ONE stack value, so two bare { } chunks side by side are two
;; separate tokens and PLAY! only ever sees the top one. Put everything
;; in ONE string instead, same multi-part support (parse ...) itself
;; already has:
S" {high: !mf g4 a4 b4 c5}" PLAY!

LATEST-TX IDS .
;; => (:high :verse)  -- both committed, in registration order

BYE
;; leaves cleanly and immediately, same idea as (exit) inside mu! above
;; -- ANS Forth's own standard word for "leave the interpreter" (not
;; EXIT/QUIT, which are real, different standard words this Forth
;; doesn't implement -- see input.forth's own comment above BYE's
;; definition). Ctrl-D still works too, but expect a several-second
;; delay before the shell prompt comes back once MIDI has been
;; CONNECTed in that session -- BYE doesn't have that delay.


4. Switching between entry points without leaving the process
=================================================================
As of this section, all three entry points are reachable from EACH
OTHER within one running Clojure REPL, not just as three separate
processes -- (mu!) already worked this way; (forth/repl!) is Forth's
own counterpart, verified live the same way the rest of this file was.

$ lein repl

(sc! "{verse: c4 d4 e4}")            ; stage+commit from plain Clojure

(forth/repl!)                        ; -> nested Forth REPL, same process
forth> S" verse" LATEST-TX CHILDREN .
;; :verse (staged by the OUTER Clojure call, not this nested loop) is
;; right there -- core.repo/musics.clj's session are defonce singletons,
;; the same store no matter which interpreter is driving them.

forth> BYE
;; => "Back to the Clojure REPL." -- returns control, does NOT call
;; System/exit the way -main's own standalone process does on the same
;; word; the outer REPL (and anything else in this JVM) is untouched.

user=> (ids)
;; => (:verse)

;; Only Forth-LEVEL state (the dictionary of user-defined words, the
;; stack) is NOT carried across a (forth/repl!) call -- each call starts
;; a fresh dictionary, same as a brand new `lein run -m input.forth`
;; process would. core.repo content always is shared, both directions.


What's NOT in this comparison, and why
=========================================
Forth's musics.clj bridge (musics-prims in forth.clj) is a fixed,
hand-written list of def-prim calls, not a live (ns-publics 'musics)
introspection -- so it only covers whatever was in musics.clj's public
API at the time it was written. times/transpose/invert/scale/reverse/
shuffle/thread/active-key/tonal-transpose/tonal-invert/snap-to-scale/
tonal-harmonize, play!/p! are all wired now (TIMES/TRANSPOSE/INVERT/
INVERT-MEAN/SCALE/REVERSE/SHUFFLE/THREAD/ACTIVE-KEY/TONAL-TRANSPOSE/
TONAL-INVERT/SNAP-TO-SCALE/TONAL-HARMONIZE/PLAY!/P!), each verified
live the same way the rest of this file was.

These combinators are deliberately, uniformly pure now -- input phase
(talking to core.repo/tx) and read-eval-play (transforming already-
materialized music) are kept structurally separate, not just as a
convention. sq and active-key are the ONLY two functions/words that
read core.repo at all (id + tx -> seq / -> Key); times/transpose/
invert/scale/reverse/shuffle/thread/tonal-* all take and return
MATERIAL -- a real, already-built seq -- and never see a bare id or a
tx themselves. This replaced an earlier design where every combinator
accepted either a bare id (resolving it via tx internally) or an
already-built seq, which is what made invert's own no-axis,
each-part-around-its-own-mean arity genuinely ambiguous with its
(axis material) arity -- both looked like a 2-arg call once the id
had already been resolved. Under the current design there's no tx
argument competing for that slot at all, so invert needs no
sniffing or special-casing: (invert material) and (axis material) are
just two clean arities, INVERT-MEAN and INVERT in Forth.

One real consequence of "material only, never a bare id": chaining
more than one of these words in Forth needs every word's own scalar
arg pushed BEFORE the material-producing chain runs (confirmed live,
not just reasoned through -- see forth.clj's own comment above its
generative-transforms block, and doc/forth-functions.txt's copy of
the same warning):
  7 2 S" verse" LATEST-TX SQ TIMES TRANSPOSE PLAY
-- not `2 S" verse" ... SQ TIMES 7 TRANSPOSE`, where 7 would land on
top of TIMES's own output and get mistaken for material by TRANSPOSE.

ks (the Key tonal-transpose/tonal-invert/snap-to-scale/tonal-harmonize
need) is always explicit now too, same as material -- there's no
"auto-resolve" special case left anywhere in this API. (active-key id
tx) / ACTIVE-KEY is simply the one place a ks value comes from in
practice, since there's still no way to build a common.music-elements
Key from bare Forth text directly. Nothing new gets added to
musics-prims automatically going forward, either -- the next
combinator added to musics.clj will need the same manual wiring these
did.

Also real, and separately documented in CLAUDE.md/doc/forth-functions.txt:
Forth's own PLAY/DISPLAY words only reach core.async-engine/play's
single-id case, not its full [:par ...]/[:seq ...] mini-language -- no
vector-literal syntax exists in this Forth to build a group with.
