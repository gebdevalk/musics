musics.lang -- parse mode: bridging real musics text
========================================================

This is a companion to `doc/musics-course.txt` (read that first if
you haven't -- this assumes you already know the stack, quotations,
and vocabularies) focused on one specific thing: how musics.lang lets
you write real musics-DSL text -- the same language a `.mus` file is
written in -- right inside an otherwise ordinary stack program, and
have it land in the shared repo the same way `(musics.core/parse ...)`
already does.

Every word this doc covers lives in the `parse` vocabulary
(`src/musics/lang/vocab/parse.clj`) -- one of the three vocabs
`scratchpad` directly `USE:`s (`{musics, parse, algo}`, see
musics-course.txt section 7), so everything below is reachable with no
extra `USE:` of your own. Every transcript below was actually run
(`lein run -m clojure.main`, not guessed), same discipline
musics-course.txt holds itself to.

A note on musics-text examples in this file: the actual bracket scheme
in `src/input/musics.ebnf` right now is `[ ]` = Sequence, `{ }` =
Parallel, `^{ }` = Context, `'[ ]` = Data -- checked directly against
the grammar file, not copied from CLAUDE.md's own prose, which has
drifted from it before (check `musics.ebnf` directly when in doubt).


1. `#: ... ;` -- the shortcut
-------------------------------

`#: ... ;` is sugar for `"..." parse-notation` -- everything between
`#:` and the next top-level `;` is captured as one literal string and
handed to `parse-notation` (parse-mode's own version of `parse`, see
section 5), which parses and commits it into the shared repo, the
exact same repo `(musics.core/parse ...)` and a loaded `.mus` file
both write into.

**A bare, unwrapped note isn't worth an id of its own.** `TopElement`
admits a bare `Leaf` directly (see CLAUDE.md's "Grammar" section), and
the walker auto-wraps one in its own throwaway one-child Sequence so it
has somewhere safe to put a note-glued dynamic -- but that wrapper's
auto-id is pure plumbing, never something you asked to name or address
again. So parse mode pushes the LEAF ITSELF for a bare note, not its
wrapper's id:

    scratchpad<0> #: c4 ;
    scratchpad<1> :type get .
    :LEAF
    scratchpad<0> #: c4 ;
    scratchpad<1> :pitches get .
    [60]

Several bare top-level leaves are each their own such throwaway wrap,
so each leaves its own leaf value on the stack -- three separate
values, not one collection (`:pitches get .` here pops one leaf at a
time, top of stack first, so `e4`'s `[64]` comes back before `c4`'s
`[60]`):

    scratchpad<0> #: c4 d4 e4 ;
    scratchpad<3> :pitches get .
    [64]
    scratchpad<2> :pitches get .
    [62]
    scratchpad<1> :pitches get .
    [60]

**Wrap it in `[ ]` yourself, on the other hand, and you get a real
id** -- you deliberately asked for an addressable Sequence, so that's
what parse mode gives you back, even for a single note:

    scratchpad<0> #: [v: c4 d4 e4] ;
    scratchpad<1> .
    :v

**Nested ids come along too, not just the outermost one.** A `{ }`
Parallel with two named branches leaves all THREE ids on the stack --
the Parallel's own id, and both of its branches':

    scratchpad<0> #: { [a: c4] [b: d4] } ;
    scratchpad<3> .s
    :p1 :a :b

This is `musics.core/parse`'s own `:all-ids` (see its docstring) --
every id the parse touched, top-level and nested, in the order it was
written (a container's own id always precedes its own children's), with
an isolated bare leaf's own wrapper substituted for its actual leaf
value instead of surfacing that wrapper's id at all. It's a genuinely
different thing from `:ids` (`musics.core/parse`'s OTHER, older key,
still there, still top-level-only, never leaf-substituted -- kept for
every caller that already relies on that narrower meaning, e.g. the
GUI). Parse mode always uses the fuller `:all-ids` list.

A failed parse still leaves exactly one value on the stack, `nil` --
never zero, so you never have to guess how many slots to inspect
before knowing whether it failed at all (see section 5).


2. What's actually happening: the tokenizer, not the interpreter
--------------------------------------------------------------------

`#: ... ;` is resolved entirely by musics.lang's own TOKENIZER
(`scan-hash-colon` in `src/musics/lang.clj`), before any word is ever
looked up -- this is why the text inside doesn't need to be valid
musics.lang syntax at all (a bare `c4` is not a musics.lang word, and
never needs to be one). The scanner just walks characters, tracking
one depth counter over `[ ] { } ( )` so a `[ ]`/`{ }` nested inside the
span doesn't confuse it, and skipping over `"..."` string literals and
`%{ ... %}` block comments verbatim (so a bracket character INSIDE
either of those can never be mistaken for real structure) -- only a
`;` at depth zero, outside any string/comment, ends the span. A `%...`
line comment (see below) needs no such care at all: `;` is the only
character with two jobs here, and `%` was never one of them.

    scratchpad<0> #: c4 % a comment
    d4 ;
    scratchpad<2> :pitches get .
    [62]
    scratchpad<1> :pitches get .
    [60]

A `;` inside `[ ] { } ( )` (bracket depth > 0), a `"..."` string, or a
`%{ ... %}` block is likewise never mistaken for the span's own
terminator -- only a genuinely bare, top-level `;` ends it.


3. Gotcha: one line only, at the live REPL
-----------------------------------------------

`run-repl-loop` (what `(musics.lang/repl!)`/`lein run -m musics.lang`
both drop you into) reads and runs ONE LINE at a time -- so a
`#: ... ;` span typed live has to open and close on that same line.
Leave it unterminated and the tokenizer runs off the end of the string
before ever seeing another line to keep looking in:

    scratchpad<0> #: [v: c4
    Error: Unterminated #: ... ; block

This is purely a consequence of how the REPL loop feeds text in, not a
limit of `#: ... ;` itself -- a genuinely multi-line span works fine
the moment the whole thing arrives as ONE string in one go, which is
exactly what happens with `(lang/run-string ctx multi-line-str)` called
directly from a Clojure REPL, or with a `.mus`-style file loaded via
`parse-file` (section 5) instead of typed as `#: ... ;` at all.


4. `parsing?` / `interpreting?` / `compiling?`
----------------------------------------------------

Three predicates report which mode the interpreter is in right now:
`parsing?` is true while a `#: ... ;` span's own `parse-notation` call
is actually running; `compiling?` is true while a `:`/`::` word's own
body is being compiled; `interpreting?` is true whenever neither of
the other two is. Worth knowing what they're good for, honestly:
because this interpreter is single-threaded and runs one word
completely before the next one starts, nothing YOU type after a
`#: ... ;` span can ever observe `parsing?` still being true -- by the
time your next word runs, `parse-notation` has already finished and
reset it:

    scratchpad<0> interpreting? .
    true
    scratchpad<0> #: c4 ;
    scratchpad<1> drop
    scratchpad<0> parsing? .
    false
    scratchpad<0> interpreting? .
    true

These exist as a hook for code invoked REENTRANTLY during a parse or a
word-compile (a future callback fired from inside `musics.core/parse`
itself, say) -- not something to poll from a sibling line at the
top-level REPL the way this transcript just tried to.


5. Beyond `#: ... ;`: `parse`, `s!`, `try-parse`, `parse-file`
-------------------------------------------------------------------

`#: ... ;` is sugar for the common case -- a literal, fixed span of
musics text. When you need to build the text yourself (string
concatenation, a template, a value read off the stack) or handle a bad
parse without a fixed `;`-delimited literal, these are the words
underneath it. All of them push ids/leaf-values individually, exactly
like `#: ... ;` does (section 1):

    scratchpad<0> "[q: c4 d4]" parse .
    :q
    scratchpad<0> "{ [a: c4] [b: d4] }" s! .s
    :p1 :a :b

`parse` -- `( text -- id/leaf* )` -- parses and commits, exactly what
`#: ... ;` calls under the hood (via `parse-notation`, which is just
`parse` run with `parsing?` held true for the duration -- see section
4). `s!` is musics.core's own short name for the identical function --
literally `(defn s! [text] (parse text))`, not a different behavior
under a shorter spelling.

A failed `parse`/`s!` prints the same formatted error `#: ... ;` would
and leaves exactly one value, `nil`, on the stack -- never zero, and
never a thrown error either:

    scratchpad<0> "[q: bogus-!]" parse .
    -- Parse error --- line 1, column 6 --
    |
    |  [q: bogus-!]
    |       ^
    |
    |  Expected one of:
    |    * ']'
    |    * comment (%{ ... %})
    |    ... and 14 more
    ------------------------------------------
    nil

`try-parse` is a genuinely different tool, not a safer `parse` --
worth being precise about, since it's easy to assume otherwise from
the name alone. Live-checked: it parses only, commits NOTHING to the
repo, and on success pushes the RAW instaparse parse tree (nested
vectors, meant for grammar debugging), not an id or a leaf at all:

    scratchpad<0> "[q: c4]" try-parse .
    [:Program [:Sequence [:Id [:Name "q"]] " " [:Note [:Pitch [:PitchLetterRel "c"]] [:DurationNum "4"]]]]
    scratchpad<0> ids .
    ()

(`ids` -- every id currently in the repo -- comes back empty: that
`try-parse` call never touched it.) On failure it prints the same
formatted parse error and pushes `nil`, same as `parse` does. If what
you actually want is "parse, but don't blow up on bad input" --
`parse` (and therefore `s!` and `#: ... ;`) ALREADY behaves that way,
so there's no separate committing-but-non-throwing variant beyond
plain `parse` itself.

`parse-file` -- `( path -- id/leaf* )` -- reads a file's text and feeds
it to `parse`, same as `musics.core/parse-file`, pushing every id/leaf
it touched the same way:

    scratchpad<0> "/path/to/example.mus" parse-file .
    :intro


6. Where this lands
-------------------------

Everything `#: ... ;`/`parse`/`s!`/`parse-file` commit goes into the
SAME global, process-wide repo every other tier of this project reads
from directly (`core.repo`'s own registry -- see CLAUDE.md's "Repo
state" section) -- not something private to one `musics.lang` context.
An id a `#: ... ;` span just introduced is immediately visible to
`find`/`children`/`inspect`/`play`/`play-add` (the `musics` vocab, see
musics-course.txt) exactly as if it had been typed into a `.mus` file
and loaded, or handed to `(musics.core/parse ...)` from a plain
Clojure REPL -- parse mode is a second entry point into the same
material, not a separate, sandboxed one. And because every touched id
lands on the stack individually, chaining straight into one of those
words needs no unpacking step at all -- `#: [a: c4] [b: d4] ; play`
plays `:b` directly (the last id pushed is the one on top), no map to
pull an `:ids` vector out of first the way a single bundled
`{:ids ids}` result would have required.
